# Serve the always-current review page

`quarterdeck serve` runs a small local web server. It reads your Firstmate homes
at startup and keeps serving the last built pages while refreshing them.
After the Needs-you cards, when any selected home or registered secondmate has
a captain board, its list appears; otherwise the shared waiting view appears, followed by
Firstmate's `/bearings` sections (Captain's Call, Underway, Charted Next).
See [See recent work](see-recent-work.md) for the waiting view and recent-work display.
Reports waiting on your review also appear. See the
[captain board reference](../reference/captain-board.md) for its file and display
rules. Serving costs no tokens and needs no Firstmate session.

## Run it

```sh
quarterdeck serve
```

Open `http://127.0.0.1:8765/`. The page leads with Needs-you cards
(see [Watch Firstmate's activity as cards](watch-activity-cards.md) for polling
and unread behavior). The page shows a "Generated at" time and reloads
itself every 60 seconds, restoring open items and sections after each refresh
when browser session storage is available. Automatic refresh waits while a reply
box has focus or contains text that is not saved in browser storage, a reaction
is selected or being sent, the view editor has unsaved changes or a pending
save, a report or wait action is being saved, or a report's **Undo** is still
offered. Saved, unfocused replies allow refresh; see [reply drafts](#react-to-calls-and-reports-from-the-page).
Each refresh downloads the whole new page before replacing the current one.
When the server cannot be reached or the download fails, the page stays as it is and shows "Can't reach Quarterdeck · last updated 3 min
ago" at the top, then tries again every 15 seconds.

The server compresses pages with gzip for any browser that asks, so a refresh
over a weak signal moves roughly a seventh of the bytes.

## Pin the page to a phone home screen

The served page names an icon and a web manifest (`manifest.webmanifest`,
`icon.svg`, `icon-180.png`, `icon-192.png`, `icon-512.png`, all generated by
Quarterdeck and read-only). In the phone's browser, use "Add to Home Screen";
the page then opens on its own, in the same address you served it from. The tab
title shows how many items need you, such as "(2) Quarterdeck · Firstmate
review", and the count goes away when nothing is waiting. A file written by
`quarterdeck render` has nothing to pin.

The server finishes its first build before accepting requests. After that,
the first request at least 30 seconds after a build finishes starts a background rebuild
and immediately receives the previous pages. Other requests also receive those
pages until the rebuild finishes; only one build runs at a time. Captain-wait
watcher updates also request a background rebuild. A failed rebuild logs the
error and keeps the previous pages, with another attempt on a request after
30 seconds unless a new invalidation requests one sooner.

For feed failures within a completed rebuild, see the
[failed-feed refresh contract](../reference/attention-json.md#failed-feed-refreshes).

With `--allow-marks`, report marks, saved views and wait discards wait for a
rebuild before responding so the page can reload with the change. A render
failure still returns the successful write result and leaves the previous pages
available. Reactions acknowledge delivery without waiting for rendering; the
card updates from the response while the server refreshes pages in the background.

To see the serving address, run `quarterdeck url`. See the
[CLI reference](../reference/cli-and-config.md) for how it determines the
address and for its JSON output.

| Option | Default | Meaning |
| --- | --- | --- |
| `--host ADDRESS` | `127.0.0.1` only | Address to bind. Repeat it to listen on several addresses, all on the same port. |
| `--port N` | `8765` | Port from 1 through 65535. |
| `--home PATH` | unset | Select one home, overriding configured homes and `FM_HOME`. |
| `--config FILE` | private user config, if present | Select homes with the same rules as `render`. |
| `--title TEXT` | configured title | Override the page title. |
| `--no-snapshot` | off | Skip the Firstmate snapshot script and always parse backlogs. |
| `--allow-marks` | off | Enable the "Mark reviewed", "Unmark", "Discard" and "Undiscard" buttons for reports, reactions sent to Firstmate, saving briefing views from the page, and "Discard this wait" on captain-wait cards. |
| `--watch-waits` | off | Also run the captain-wait watcher in the background; see [Track what is waiting on you](track-captain-waits.md). |
| `--tls-cert FILE` | unset | Serve `https` with this PEM certificate chain. Give `--tls-key` with it. Phone notifications need `https`. |
| `--tls-key FILE` | unset | The PEM private key for `--tls-cert`. |

By default the server serves generated pages and read-only assets and has no
write endpoints. `--allow-marks` enables the actions described below; see the
[CLI reference](../reference/cli-and-config.md) for the
allowed endpoints. When snapshots are enabled, Firstmate's wrapper may refresh
its cache and read registered remote secondmate ledgers through its own routes;
`--no-snapshot` skips that behavior.

## Get phone notifications

With `--allow-marks`, the served page can send your phone one notification
whenever a new item needs you: a desk call, a held task, or an open decision in a
[topic thread](keep-topic-threads.md). The notification shows the item's title
only, such as a decision's question, never its recommendation or detail;
tapping it opens Quarterdeck on that card. When Firstmate answers a question you
sent from a topic thread, one notification says "Firstmate answered" with the
topic's title. The same item never sends a second alert. Withdrawal behavior
depends on the phone browser, as described below.

### What the server needs

- `--allow-marks`, as for every other write from the page.
- Snapshot reads enabled (omit `--no-snapshot`). With `--no-snapshot`, phone
  notifications are off because Quarterdeck cannot tell when a needs-you item
  is answered; the controls and push endpoints are unavailable.
- The Python `cryptography` package for the Python that runs Quarterdeck
  (`python3 -c "import cryptography"` succeeds). Without it the control does not
  appear, and `serve` prints "Phone notifications: off" at start-up.
- An `https` address the phone trusts. Phone browsers allow notifications only
  on `https`, and an iPhone also needs the page added to its Home Screen from
  that address (iOS 16.4 or later). Serve with `--tls-cert` and `--tls-key`, or
  put Quarterdeck behind a TLS reverse proxy. On plain `http` the control stays
  hidden.
- Outgoing `https` from the server to the phone's push service (Google for
  Android Chrome, Apple for iPhone).

### Turn them on, once per phone

On an Android phone with Chrome:

1. Open Quarterdeck's `https` address.
2. Tap **Turn on notifications** in the header, then allow notifications.

On an iPhone:

1. Open Quarterdeck's `https` address in Safari.
2. Tap Share, then **Add to Home Screen**. If Quarterdeck is already on the Home
   Screen from an `http` address, remove that icon first.
3. Open Quarterdeck from the new Home Screen icon.
4. Tap **Turn on notifications** in the header, then **Allow**.

The header then shows "Notifications: on". In a Safari tab it shows
"Notifications: add Quarterdeck to the Home Screen first" instead. If the
browser blocked notifications earlier, the header says so; allow them for this
site in the browser or phone settings and reload.

### What arrives, and when it goes

- One notification for each Needs-you card that appears after the server
  starts tracking. Items already waiting at the first complete observation are
  recorded, not announced. While a subscription exists, the server checks about once a
  minute even when every browser is closed.
- When the item is answered or goes away, Quarterdeck withdraws its
  notification on Android and desktop browsers. An iPhone allows no silent
  withdrawal, so no withdrawal push is sent there; the notification is cleared
  the next time you open Quarterdeck. Chrome may occasionally show its own
  generic "updated in the background" line after a silent withdrawal.
- An item that goes away and comes back stays quiet. A new hold on the same
  task counts as a new item.
- While the Needs-you feed cannot be read in full, nothing is withdrawn and
  unfamiliar items wait for a complete observation before being announced.

### Turn them off

Tap **Turn off notifications** in the header. Removing the Home Screen app or
blocking notifications in the phone's settings also works: the push service
then reports the subscription gone, and Quarterdeck deletes it on its next
message. See [Privacy and architecture](../explanation/privacy-and-architecture.md)
for other subscription removal rules, what each message contains and where the
keys and subscriptions are stored.

## Mark reports reviewed from the page

```sh
quarterdeck serve --allow-marks
```

The page then shows "Mark reviewed" on each report waiting for review, and a
collapsed "Reviewed reports" section with "Unmark". Each click calls the same
code as `quarterdeck reports mark-reviewed` / `unmark-reviewed`, stores the
same content fingerprint in the same state database, and reloads the page. A
report that changes afterwards returns to "needs review". **Discard** takes a
report off the list without marking it reviewed; discarded reports are in a
collapsed "Discarded reports" section with **Undiscard**. Each report's own
page carries the same buttons above the document; after a click it offers
**Back to Quarterdeck** instead of reloading.

There is no key or login: anyone who can open the page can mark or unmark
reports, and clicking the button just saves the mark. See
[Privacy and architecture](../explanation/privacy-and-architecture.md) for
request restrictions and review-mark storage. `quarterdeck service
--allow-marks` writes the flag into the systemd unit. Backlog and board items
cannot be marked.

When you bind to a non-loopback address with `--allow-marks`, everyone who can
reach the page can change review marks, send reactions and edit saved views.
Use marks only on a network you trust, or put the server behind an
authenticating TLS reverse proxy.

## React to calls and reports from the page

With `--allow-marks`, each desk call, related item and report also has
**Approve**, **Hold**, **Not now** and **Question** buttons, a reply box
and **Send**. Pick a reaction, write a reply, or both, then Send.

Calls on Needs-you cards, the desk and related cards can also show answer
buttons taken from their own text. Quarterdeck recognizes `Answer:`, `Option:`,
`Choice:` (also their plurals), `Reply:` or `Respond:` at the start of the text
or a new line. These accept quoted answers or an unquoted list separated by
commas, `or`, or a slash surrounded by whitespace, such as
`Options: merge release/63 or hold.` Slashes within an answer stay literal.
Unquoted lists need at least two answers and reject the whole list if any
answer exceeds four words. Parsing stops before a later sentence, semicolon
or recommendation field.

Positive `Answer`, `Reply`, `Respond`, `Say`, `Send`, `Type` or `Tell` directives
in the same position accept immediately listed quoted answers, such as
`Reply 'merge 63' or 'hold'.` Quoted answers must be 2–30 characters and at most
four words. Ambiguous prose can leave the card without answer buttons; at most
four distinct answers are shown. Tapping one sends that phrase immediately as
a plain reply, ignoring any selected quick reaction and preserving both that
selection and the reply draft. Use the reply box for anything else.

The reply box is a text area that grows as you type for a long dictated answer; the
[reaction text limit](../reference/cli-and-config.md#reactions) applies.
A counter appears when you near the limit, and a
longer reply is refused with a message rather than cut. An unsent reply is kept
in this browser's `localStorage` (for up to seven days) across reloads when
storage is available. Reply text is shared between card and desk composers for
the same item and kind. A successful **Send** clears the submitted text from those
composers and storage; edits made while sending survive. A failed send keeps
the draft. Quarterdeck
hands one line (item ID, task ID, reaction, your text and the time) to the
item's home through its `bin/fm-inbox.sh note`, so Firstmate receives it as a
note and wakes, and it routes the answer to you or the workers. The card shows
"Sent to Firstmate" and then the latest reaction from either this page or the
cloud artifact. If the home has no executable `bin/fm-inbox.sh`, or it fails,
the card says "Not sent" and nothing is recorded; send it again.

As with marks, there is no key: anyone who can open the page can send
reactions as you, so use `--allow-marks` only on a network you trust.

With `--allow-marks` and the captain-wait watcher, a card for a task held for
you also has **Discard this wait**. After you confirm, Quarterdeck sends the
home's Firstmate a note through the same `bin/fm-inbox.sh note` asking it to
drop the hold, and hides the card once the note is delivered. See
[Track what is waiting on you](track-captain-waits.md#discard-a-wait).

## Where the sections come from

When any home keeps [topic files](keep-topic-threads.md), the served front page
is the short one (Needs you, Changed since you last looked, the ask box and
search), and the sections below appear on `classic.html` for this release.

When a home has an executable `bin/fm-bearings-snapshot.sh`, Quarterdeck runs it
with `--json` and `FM_HOME` set, under a 15-second timeout, so the page and
`/bearings` agree. For decisions with a matching local backlog item, the page
adds hold context, task body, options and recommendation where present, filing
date, project, and a report link. Remote decisions retain the snapshot summary
and point to the secondmate home for full background. If the script is
missing, fails or times out, Quarterdeck parses the backlog itself and the
page's "Sources" line says the fallback was used and why. That script may
refresh Firstmate's own cache as part of its normal operation; pass
`--no-snapshot` to avoid running it.

## Run it in the background with systemd

Print a user unit, or write it:

```sh
quarterdeck service            # print the unit
quarterdeck service --write    # write ${XDG_CONFIG_HOME:-~/.config}/systemd/user/quarterdeck.service
systemctl --user daemon-reload
systemctl --user enable --now quarterdeck.service
```

`service` accepts the same `--host` (repeatable, default 127.0.0.1 only),
`--port`, `--home` and `--config` options as `serve`, plus `--allow-marks` to
enable report review marks in the unit. It never runs `systemctl` itself. The
unit it writes looks like:

```ini
[Unit]
Description=Quarterdeck read-only Firstmate bearings page
After=network.target

[Service]
ExecStart="/usr/bin/python3" "/path/to/quarterdeck.py" "serve" "--host" "127.0.0.1" "--port" "8765"
Restart=on-failure
RestartSec=5

[Install]
WantedBy=default.target
```

To keep it running when you are logged out, run `loginctl enable-linger $USER`.

For example, `quarterdeck service --host 127.0.0.1 --host ::1 --write` binds
both loopback families; the unit carries one `--host` per address.

## Security: loopback by default

The page contains real task names, hold reasons, reports and paths. There is
**no login**. Binding a non-loopback address (for example `--host 0.0.0.0`)
exposes that work data to everyone who can reach the port on that network.
Quarterdeck prints a warning when you do. Prefer the default, and reach it
remotely through an SSH tunnel or an authenticated reverse proxy you control.
